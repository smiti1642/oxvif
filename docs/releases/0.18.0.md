recordings at an absolute UTC position from Rust. The CLI adds one-shot
device queries, live event watching and shareable diagnostics. Cameras that expose Media2 also get
source-scoped overlay and privacy-mask workflows.

## CLI and automation

- **Query a camera without setup.** Run `oxvif inspect 192.168.1.100 --username admin`
  for live device information. Use `--read profiles`, `--read capabilities`,
  or `--read services` for more data. Use `--read stream-uri --profile TOKEN`
  for the profile's live RTSP URL. Supply the password at a hidden prompt,
  with `--password` for a single-line command, or through stdin for automation.
  Inline passwords may be visible in shell history and process arguments.
  The query leaves the local inventory and credential store untouched.
- **Watch live events from one camera.** Run
  `oxvif --device front-door events watch --duration 30s --output jsonl`.
  Use `--topic` to select one exact ONVIF topic. The terminal shows counts.
  JSONL emits notifications, gaps and a final summary. Slow output pauses
  pulling while the subscription keeps renewing. Ctrl+C requests unsubscribe.
- **Share a diagnostic report.** Add `--share` to a single-device `diagnose`
  or to `config validate`. The standalone JSON identifies the failed stage,
  suggests what to check next, and shows which checks were skipped. It omits
  credentials, addresses, local paths and raw device responses. A failed check
  can still produce a valid report.
- **Integrate the CLI into a console.** `describe --grammar --output json`
  exports a versioned command tree with arguments and execution capabilities.
  Apps can use it for help and completion, and use `--control-stdin` to
  stop an event watch and read the final cleanup result.
- **Choose the media service.** Use `--media-service media1`, `media2` or
  `auto` for profiles, URIs, diagnosis, inventory and health media reads.
  `auto` tries advertised Media2 first and falls back when its endpoint is
  missing or the device explicitly reports an unsupported operation.
  Without the flag, `media profiles` uses Media1 and `data.result` is an
  array. With an explicit selector, `data.result` is an object with
  `profiles`, `media_service`, `endpoint_source` and `attempts`. Both forms
  use JSON/JSONL envelope schema v3.
- **Match the camera's SOAP authentication.** `--soap-auth` accepts
  `combined` (the default), `digest` or `ws-security`. Automatic clock
  synchronization uses device time for WS-Security UsernameToken.
- **Probe a stream on demand.** Run
  `oxvif --rtsp-probe describe diagnose CAMERA` to inspect SDP and the
  advertised video codec. `packet` also runs SETUP and PLAY, waits for one
  interleaved video RTP packet, and attempts TEARDOWN. Both modes leave
  `playback_verified` false. The stream must use the device host. HTTPS
  device URLs require RTSPS and certificate verification.
- **Read complete health output.** `oxvif health check --details` shows
  every check and timing in the terminal. `-vv` sends bounded session and
  retry diagnostics to stderr. JSON and JSONL reports include all checks.
- Direct camera authentication accepts an empty password when a username is
  supplied with the password value explicitly set to empty.

See the [CLI guide](https://github.com/smiti1642/oxvif/blob/v0.18.0/docs/oxvif-cli.md).

## Rust upgrade notes

These migration notes apply when upgrading from the public 0.17.0 release
or a checkout of the security-only 0.17.1 tag.

- **Handle incomplete recording searches.** `search_recordings()` returns
  `OnvifError::RecordingSearchIncomplete` when a limit, cancellation or an
  unknown state ends the search before Completed. RPC failures propagate
  as their original errors. Use `search_recordings_with_report()` to retain
  partial records, the failure reason and the independent
  `EndSearch` outcome. Call `close()` on an owned search for remote cleanup.
- **Update exhaustive matches.** Account for
  `OnvifError::RecordingSearchIncomplete`, `TransportError::Deadline`,
  `TransportError::ResponseTooLarge`, `SoapError::ResourceLimit`, and
  `HttpTransportBuildError::{InvalidTimeout, InvalidResponseLimit}`.
  Complete struct literals for the CLI library's `ExecutionOptions` need
  `soap_auth`, `media_service` and `rtsp_probe`. Use
  `..Default::default()` for fields that can take their defaults.
- **Check production SOAP fixtures and custom transports.** The response
  validator requires complete XML and enforces limits of 4 MiB, depth 64
  and 65,536 elements, including responses from custom transports. The
  built-in HTTP transport defaults to ten seconds per HTTP request and a
  4 MiB response limit. Scoped operations can apply a deadline to the
  entire SOAP exchange, including a Digest challenge and retry.
- **Use explicit captures for wire investigation.** Client trace logs now
  record operation, timing, byte count and error class. Capture wire
  messages explicitly and review device data before sharing a capture.

See the [Rust library guide](https://github.com/smiti1642/oxvif/blob/v0.18.0/LIBRARY_GUIDE.md).

## New Rust workflows

- Managed pull-point subscriptions preserve qualified topics and endpoint
  parameters, renew while polling, report gaps after recovery, and support
  asynchronous close. Consumers can request a topic filter, stop polling with
  a cancellation handle, drain queued notifications and inspect cleanup.
- **Recover event monitoring after an interruption.** Opt in with
  `OnvifSession::managed_events_recovering()`. When a replacement PullPoint
  supports persistent notification storage, oxvif attempts to seek and read
  retained events. Otherwise it requests the current property state.
  Repeated snapshots of the same property value within one synchronization
  are coalesced, and a gap remains visible even when some events are recovered.
- **Start and seek recording replay by UTC.** Enable the `recording-replay`
  feature and call `OnvifSession::start_recording_replay()`. Read the H.264
  RTP packets on one interleaved RTSP/TCP video track and call
  `ReplaySession::seek()` to reposition the same session. Start evidence
  includes the requested time, the server's PLAY range when available, and
  the first correlated RTP access-unit time. Confirm the first decoded frame
  with a video decoder. A recording gap is reported when the observed
  section boundaries support it.
- `health::snapshot::SnapshotError::kind()` exposes typed error categories.
  `http_status()` returns the status when the endpoint returned one.
- Typed PTZ movement supports separate pan/tilt and zoom axes, coordinate
  spaces, speed, continuous timeout, and axis-specific Stop.
- Media2 text OSD and polygon privacy masks are scoped to their source
  configuration. Writes support independent read-back. A lost reply can
  produce `OutcomeUnknown`, so read the current state before retrying.
- Read or update supported Media1/Media2 audio configurations, read
  Analytics modules and rules, parse metadata XML, search the recording
  timeline and events, and manage remote export jobs. The optional
  `talkback` feature sends one half-duplex PCMU track. The optional
  `recording-download` feature downloads from an explicit URL and
  preserves existing destination files.

## Mock and replay

- Raw HTTP fixtures should send SOAP 1.2 `application/soap+xml` with a
  valid action parameter for dispatch. Malformed headers can return HTTP
  400 and unsupported representations return 415. Recognized SOAP
  Sender faults use HTTP 400, and other standard SOAP fault codes use 500.
  Legacy nonstandard fault codes and malformed raw responses use 200.
- Create a PullPoint before emitting test events and use the returned
  endpoint for pulling, renewing and unsubscribing. With mock authentication
  enabled, generate fresh UsernameTokens for successive positive requests.
- Recording searches now have isolated snapshots, pagination and expiry.
  `EndSearch` releases the search, and unknown or expired tokens return
  a fault. Media1 and Media2 share mock OSD state. Privacy masks belong
  to the individual mock instance.
- Metamorph compares reviewed fields for 16 SOAP Actions and can compare
  ordered event windows. Search and PullPoint lifecycle calls use live
  state during replay.

See the [Mock server guide](https://github.com/smiti1642/oxvif/blob/v0.18.0/docs/mock-server.md) and the
[interoperability verification record](https://github.com/smiti1642/oxvif/blob/v0.18.0/docs/active/onvif-interoperability-plan.md#i07i10-delivery-evidence).

## Dependencies and verification

The workspace lockfile includes `tokio-rustls 0.26.6`,
`rustls-native-certs 0.8.5`, `tokio 1.54.1`, `quinn-proto 0.11.19`,
`quinn-udp 0.5.16` and `rustix 1.1.6`. Library users can update these
dependencies in their own application's lockfile. Native credential storage
uses `keyring 3.6.3`. The local dependency audit found zero vulnerabilities
and three existing maintenance warnings in the Linux credential dependency
graph.

The Windows candidate passed workspace tests and strict Clippy with all
features enabled, plus the Rust 1.88 workspace build check. Cargo packaged and
verified both the SDK and CLI locally. Release staging built the CLI for all five
targets and verified Homebrew installation and bottle reinstallation on Intel
and Apple Silicon Macs, plus signed APT installation on amd64 and arm64 Linux.
[Distribution verification](https://github.com/smiti1642/oxvif/actions/runs/44281772306)

On a GeoVision GV-TBL8810, `inspect --password` read device information,
listed two media profiles and returned a distinct live RTSP URI for each
profile. The isolated configuration directory stayed absent. The live RTSP
check covered URI retrieval.

Local loopback and synthetic fixtures cover UTC replay, seeking on the same
connection, start-time evidence, and recording gaps. ONVIF schema checks
cover the applicable SOAP workflows. One real camera was used to verify
event recovery without persistent storage. After both an HTTP 503 and a TCP
interruption, monitoring resumed, the gap stayed visible, and 22 received
state notifications became 11 displayed snapshots. Persistent event history
still requires compatible hardware.

The 2026-11-18 hardware probe found six device configurations advertising
Recording, Search and Replay. Five denied recording access, and the sixth
returned no recordings. The probe found no playable recording, so UTC
start, seeking on the same session and first decoded frame time remain
unverified on hardware.
